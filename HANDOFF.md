## 1. Project Overview

### What this is

**VoucherVault Plus+** (`gregbtm/VoucherVault`) is a fork of
[l4rm4nd/VoucherVault](https://github.com/l4rm4nd/VoucherVault), a Django
web app for storing/managing vouchers, gift cards, coupons, and loyalty
cards as an installable PWA. Upstream provides: mobile-optimized UI,
offline support, QR/barcode scanning, multi-user login with OIDC SSO, and
Apprise-based expiry notifications.

This fork's goal: extend upstream into a full personal-finance-adjacent
tool — REST API, AI-assisted scanning (OCR), shared wallets, digital wallet
passes (Apple/Google), a rules-based notification engine, an MCP server for
AI-assistant access, Firefly III budget sync, an enrichment/recommendation
engine, and extensive mobile/UX polish — **without ever rewriting a line of
upstream's own code**. Per the README, this is currently "94 rounds of work
adding 436 individual features and fixes" on top of upstream.

### Relationship to upstream — what must never be touched vs. fork-owned

- **Never touched**: upstream's existing models, views, and templates are
  never rewritten in place. New functionality is added as new files, new
  fields (via migration), or new apps alongside them. This is what makes
  upstream syncs a plain `git merge` instead of a rewrite-and-reconcile
  exercise — see `docs/UPSTREAM_SYNC.md` for the full sync process (a
  10-day-cooldown detection step, risk assessment of what upstream commits
  touch, a PR with the merge result, full test suite run before merge).
- **Fork-owned, freely modified**: everything under `api/`, `dms/`,
  `imports/`, `notify/`, `ocr/`, `mcp_server/`, `deeplink/`, `help/` (all
  fork-added Django apps), plus fork-added files inside `myapp/` (e.g.
  `myapp/webhooks.py`, `myapp/portainer.py`, `myapp/views_enrichment.py`,
  `myapp/enrichment_scheduling.py`, `myapp/services/`). Nearly every
  template has fork-added sections (help-links, extra fields, extra cards)
  layered into upstream's original markup — treat additions as fair game,
  but check for `{% comment %}` markers or structural cues before ripping
  out anything that might be upstream's own original code.
- **Two independent version numbers**, both plain-text files at repo root:
  - `VERSION` (currently `1.1.165` on `main`; check `cat VERSION` fresh —
    CI bumps this on every merge, so it will have moved by the time this
    is read) — this fork's own version, auto-bumped by CI's
    `release` job on every merge to `main`, regardless of source.
  - `UPSTREAM_VERSION` (currently `1.29.0`) — the upstream release this
    fork is synced to. Only bumped on an actual upstream sync. GitHub issue
    **#54** is an auto-generated, self-updating tracker currently showing
    upstream is 7 commits ahead (including a v1.30.0 release) — not an
    actionable bug, just a sync reminder.
- **Changelogs**: `CHANGELOG.md` is auto-generated by CI (conventional-commits
  style, one entry per merged PR, machine-maintained — don't hand-edit).
  `FORK_CHANGES.md` (~7000 lines) is the real, hand-written, phase-by-phase
  narrative history of everything this fork has done — the single best
  place to search before assuming a decision was made without reason.
  `PHASE_1_TO_5_CHANGELOG.md` is a narrower, older narrative doc covering
  one specific early work cycle (query optimization, Smart Categories,
  mobile/a11y polish, webhook retry) — effectively superseded by
  `FORK_CHANGES.md` going forward; don't treat it as the canonical log.

## 2. Architecture & Key Decisions

### Additive-only pattern

Every phase in `FORK_CHANGES.md` adds new models/views/migrations alongside
upstream's code rather than modifying it in place. When adding a new
feature: prefer a new Django app (see `notify/`, `dms/`, `imports/`, `ocr/`
as examples) or new fields via migration over editing an existing
upstream model's fields. This is a deliberate constraint, not incidental
style — it's what keeps `docs/UPSTREAM_SYNC.md`'s merge-based sync process
low-risk.

### Database engine

`DB_ENGINE` env var (`myproject/settings.py:199`) selects `sqlite3`
(default) or `postgres`. SQLite is the default/recommended path for
single-instance self-hosted deployments (see `docker/docker-compose-sqlite-*.yml`);
Postgres is supported via `docker/docker-compose-psql.yml` for anyone who
wants it, using `POSTGRES_HOST`/`POSTGRES_PORT`/`POSTGRES_USER`/
`POSTGRES_PASSWORD`/`POSTGRES_DB` env vars. No engine-specific ORM tricks are
used deliberately, so tests run identically on either backend.

### Settings: env vars vs. `SiteConfiguration` DB singleton

Two tiers, and it matters which one to touch for a new feature:

1. **Bootstrap/infra settings** — read once at process start in
   `myproject/settings.py`'s "APP-LEVEL / FEATURE ENV VARS" block
   (`SECRET_KEY`, `DOMAIN`, `DB_ENGINE`, `REDIS_URL`, `OIDC_*`,
   `SESSION_*`, etc.). These must be env vars because they're needed
   before the app can even reach the database.
2. **Everything else** — lives in `myapp.models.SiteConfiguration`
   (`myapp/models.py:1055`), a singleton row (always `pk=1`), editable at
   runtime from the in-app Site Settings page (superuser-only, see
   `myapp/views.py::site_settings`). App code reads
   `SiteConfiguration.load()` fresh from the DB on every call — **never
   cached at the Python/settings-module level**, because uWSGI runs
   multiple worker processes and Celery's worker/beat run as separate
   processes again, none of which share in-memory state. The env var of
   the same name (e.g. `OCR_BACKEND`, `NTFY_DEFAULT_SERVER`) is now purely
   the seed value used the first time the singleton row is created via a
   data migration — i.e. the *documented default for a fresh install*, not
   the live value once Site Settings has been touched. **When adding a new
   configurable feature, add the field to `SiteConfiguration`, not a new
   env var**, unless it's genuinely a bootstrap-level concern.

### MCP server (`mcp_server/`)

`mcp_server/server.py` (369 lines) exposes 21 `@mcp.tool()`-decorated
functions (`search_items`, `get_item`, `create_item`, `update_item`,
`delete_item`, `add_transaction`, `mark_item_used`, `set_item_archived`,
`get_analytics_summary`, `get_expiry_timeline`, `get_expiring_items`,
`list_wallets`, `create_wallet`, `list_tags`, `list_webhooks`,
`list_wallet_activity`, `list_notification_rules`,
`create_notification_rule`, `delete_notification_rule`,
`list_item_documents`, `get_user_preferences`, `update_user_preferences`,
`list_dms_providers`, `list_dms_sync_logs`).

Key design decision (stated in `mcp_server/client.py`'s docstring): the MCP
server **never touches the Django ORM directly and never duplicates
business logic**. Every tool call becomes exactly one HTTP request via
`VoucherVaultClient` (`mcp_server/client.py`) against the existing REST API
at `myproject/api/v1/`, authenticated with `Authorization: Token
{VOUCHERVAULT_API_TOKEN}`. This means the same permission checks,
validation, and side effects (webhook events, QR/barcode generation) that
already gate the web UI and API gate MCP tool calls too — there's no
separate code path to keep in sync. `VOUCHERVAULT_BASE_URL` and
`VOUCHERVAULT_API_TOKEN` are required env vars for the MCP server process
(see `docs/MCP_SERVER_SETUP.md`; deployed via `mcp_server/Dockerfile`).

### OCR / "Scan with AI" backend selection

`ocr/backends/__init__.py` is the single dispatch point:
- `BACKENDS` dict maps `'tesseract' → TesseractOCRBackend`, `'claude' →
  ClaudeOCRBackend`, `'openai' → OpenAIOCRBackend` (classes in
  `ocr/backends/tesseract.py`, `claude_backend.py`, `openai_backend.py`,
  each implementing the `OCRBackend` interface from `ocr/backends/base.py`).
- `ocr_backend_name()` reads `SiteConfiguration.load().ocr_backend` (not an
  env var at runtime — see settings tier note above).
- `get_backend()` raises `ValueError` if the configured name isn't in
  `BACKENDS` (covers `'none'` and typos alike — both are "OCR disabled").
- Both AI backends deliberately set `temperature=0` (see Gotchas — this
  wasn't the case originally and caused non-deterministic re-scans).
- `ocr/enrichment.py`, `ocr/validation.py` handle post-extraction field
  validation/normalization, separate from the backend call itself.

### Firefly III sync

Not a full two-way sync — it's a one-directional push, implemented as a
`NotificationRule` backend (`backend='firefly'` in
`notify/models.py::NotificationRule.BACKEND_CHOICES`). `notify/backends/firefly_backend.py::_do_firefly_push(config, item, transaction)`
POSTs a single transaction to Firefly III's API per notify event, writing
the returned Firefly transaction ID back to
`transaction.firefly_transaction_id` on success. Deposit vs. withdrawal is
inferred from the transaction value's sign. `item.firefly_account_id` (set
once when linking an item to a Firefly account) takes priority over
`config.get('account_id')`. Failed pushes are retried via
`notify.models.WebhookRetry`/`FireflyTransaction` (see
`notify/migrations/0007_fireflytransaction_webhookretry.py`) — check
`notify/tasks.py` for the retry task before assuming a failed push is
silently dropped. `notify/signals.py::handle_item_value_change` is a
`post_save` receiver on `myapp.Item` that auto-creates a compensating
`Transaction` (and fires `notify_balance_changed`) whenever an item's
`value` field changes outside the normal transaction flow, specifically to
keep Firefly's ledger in sync with manual value edits — skipped for new
items, items with no `firefly_account_id`, and archived items.

### Two independent webhook systems — don't conflate them

- **`myapp.models.UserWebhook`** (`myapp/models.py:901`) — the Developer
  Hub "Outbound Webhooks" feature. Fires on `item_created`, `item_used`,
  `item_archived`, `item_balance_changed`, `item_expiry_warning`.
  Dispatched via `myapp/webhooks.py::fire_user_webhooks(user, event_type,
  item)` — fans out to every matching enabled webhook in a **daemon
  background thread** (not Celery) so the calling request is never
  delayed. Optional HMAC-SHA256 signing (`X-VoucherVault-Signature:
  sha256=...`) when the webhook has a `secret` set; always sends
  `X-VoucherVault-Event`. Payload built by `_build_payload()` — item id,
  name, issuer, type, value, currency, expiry_date, is_used, is_archived
  only, nothing more sensitive.
- **`NotificationRule` with `backend='webhook'`** (`notify/backends/webhook.py`)
  — part of the general notification-rules engine (see below), a
  different, richer event vocabulary, supports digest batching, goes
  through the Celery task pipeline rather than a bare thread.

Both exist because they were built for different purposes at different
phases (n8n/Zapier automation vs. general notification delivery) — this is
known duplication, not an oversight, but be aware a new "fire a webhook"
feature request might mean either one depending on context.

### Notification rules engine (`notify/`)

`NotificationRule` (`notify/models.py:7`) is per-user, per-channel
config: `backend` (one of `apprise`/`discord`/`email`/`firefly`/`ntfy`/
`telegram`/`webhook`/`webpush`), a JSON `config` blob (backend-specific),
`event_types` (JSON list from a 12-entry `EVENT_CHOICES` — expiry warnings,
item lifecycle, balance changes, sharing, wallet membership, merchant
health alerts, etc.), `digest_frequency` (`immediate` or `daily` — daily
batches matching events into one combined message), and `apply_to_all`
(apply to every item with no per-item wiring needed). `unique_together =
('user', 'name')`. The legacy single `apprise_urls` field on `UserProfile`
and its own Celery task are **untouched and still work independently** —
`apprise` remains a rule backend choice specifically for users migrating
off that legacy path, not a replacement that breaks it.

## 4. Deployment Specifics

### How the live instance (nasmatrix.app, Synology + Portainer) actually deploys

**Git-based, not image-based.** Portainer's stack is configured with
Build method `Repository`, pointing at `https://github.com/gregbtm/VoucherVault`,
ref `refs/heads/main`, compose path `docker/docker-compose-sqlite-build.yml`
(or `-full-build.yml` for the fuller stack). Portainer clones the repo
itself and runs `docker build` from `docker/Dockerfile` — **it does not
pull a pre-built image**, despite CI also building and pushing one to
Docker Hub (see below — that image push is effectively vestigial for this
particular deployment). On every container start, `docker/entrypoint.sh`
runs `python manage.py migrate` automatically, so schema changes need no
manual step on redeploy. See `docs/SYNOLOGY_NAS_SETUP.md` for the
one-time NAS/Container-Manager setup and `docs/AUTO_DEPLOY.md` for the
webhook mechanics below.

**What triggers a live redeploy** — two mechanisms, both off by default,
both hitting the same Portainer stack webhook URL
(`https://<portainer-host>:9443/api/webhooks/<uuid>`):
1. **In-app "Redeploy now" button** — `myapp/portainer.py`, superuser-gated
   server-side. Reads `PORTAINER_WEBHOOK_URL` from `SiteConfiguration`
   (takes effect immediately, no restart) with the env var of the same
   name as the seed/fallback.
2. **`.github/workflows/portainer-redeploy.yml`** — fires on every push to
   `main` plus manual `workflow_dispatch`. POSTs to
   `PORTAINER_WEBHOOK_URL` stored as a **GitHub repo secret** (not the
   Site Settings value — this is CI, a separate config point). If the
   secret isn't set, it logs and exits 0 — never fails CI. Requires the
   Portainer webhook endpoint to be reachable from the public internet.

**CI pipeline** — `.github/workflows/conventional-commits.yml` (workflow
name `CI`), on push-to-main and PRs:
- `changelog` (main-only) — updates `CHANGELOG.md`.
- `test` — Django + JS test suites, `npm audit --audit-level=high`,
  `manage.py check`. Runs on PR and push.
- `bandit`, `grype`, `semgrep`, `pip-audit`, `secret-scan` (TruffleHog),
  `trivy` — security scans, PR and push.
- `zap-scan` — DAST baseline, `continue-on-error: true` (advisory only).
- `deploy` (main-only, "Deploy Image") — needs all scan jobs green;
  builds a multi-arch (amd64/arm64) image via `docker/build-push-action`
  and pushes to Docker Hub as `docker.io/<DOCKER_HUB_USERNAME>/vouchervault`
  (secrets `DOCKER_HUB_USERNAME`, `DOCKER_HUB_ACCESS_TOKEN`). **This
  image is not what nasmatrix.app runs** — the live instance builds from
  source via git, per above. A comment in the workflow file itself
  confirms this fork doesn't rely on the Docker Hub image for its own
  deployment.
- `release` (main-only, "Version bump & Release") — needs only
  `[changelog, test]`, **deliberately not gated on the security scan
  jobs** (an in-file comment notes those have historically failed on
  every push to main and would otherwise block versioning entirely).
  Bumps `VERSION`'s patch number, commits `chore: bump VERSION to X.Y.Z
  [skip ci]`, tags `vX.Y.Z`, pushes to main, creates a GitHub Release.

**What actually gates a real redeploy of the running instance**: `test`
passing → `release` bumping VERSION/tagging → `portainer-redeploy.yml`
firing the webhook (if the secret is configured) → Portainer git-pulls and
rebuilds → `entrypoint.sh` auto-migrates. No SSH or manual
`docker-compose` command needed for routine updates.

## 5. Gotchas & Learnings

- **`AXES_ENABLED = 'test' not in sys.argv`** (`myproject/settings.py:551`)
  — django-axes's `AxesBackend` requires a `request` object passed into
  `authenticate()`, which Django's test client doesn't provide, so axes
  auto-disables under `manage.py test`. `LoginLockoutTests` re-enables it
  via `@override_settings(AXES_ENABLED=True)` for the one test class that
  actually needs it, since it POSTs to the real login view instead of
  using the `client.login()` shortcut. If a new lockout-related test
  mysteriously never triggers axes, check this first.
- **The Celery/Redis test-suite time bomb**: `myproject/settings.py` gates
  an in-memory Celery broker + local-memory cache + a fast password
  hasher behind `if 'test' in sys.argv:` (same pattern as `AXES_ENABLED`),
  specifically so `manage.py test` never touches a real Redis host that
  doesn't exist in CI/sandbox environments. If this gate ever regresses, a
  `redis.exceptions.ConnectionError` traceback will reappear in test
  output — treat that as broken, not expected noise; it previously caused
  the suite to burn ~1000s retrying a doomed connection (1037s → 13.6s
  once fixed). **In any sandbox where you need a live dev server (not just
  `manage.py test`), you must start an actual `redis-server` and set
  `REDIS_URL` — the gate only protects the test runner, not
  `runserver`/`shell`.**
- **`-webkit-tap-highlight-color` invalid-CSS bug** — see Section 3, PR
  #189. A bare property declaration with no selector directly inside an
  `@media` block is invalid CSS that every browser silently drops with no
  console warning. If a CSS "fix" looks present in source but visibly
  isn't working, check it actually parses (wrap it in a real selector,
  even `*`) before assuming the bug is elsewhere.
- **ItemEnrichmentField access-control gap** (Phase mid-200s,
  "Enrichment web dashboard") — `myapp/views_enrichment.py` views were
  only `@login_required`, but `EnrichmentConfig`/`EnrichmentRun` have no
  `user` FK (they're app-wide), so any authenticated user could view every
  account's enrichment runs and trigger/approve/reject organization-wide
  field changes. Fixed with a `superuser_required` decorator (same inline
  `is_superuser` pattern as `trigger_portainer_redeploy`) on every
  admin-only view. **Any new app-wide (non-per-user) model/view needs the
  same explicit superuser gate — `@login_required` alone is not enough.**
- **CSP nonce rollout** — `unsafe-inline` was removed from `script-src`;
  all inline `<script>` blocks across templates now need
  `nonce="{{ request.csp_nonce }}"`
  (`CONTENT_SECURITY_POLICY_NONCE_IN = ['script-src']`). **Any new inline
  `<script>` block in a template needs this nonce attribute or it will be
  silently blocked in production** (works fine with `DEBUG=True` looseness
  in some setups — test with the real CSP header if a new inline script
  mysteriously doesn't run). Separately, `CSP_FRAME_ANCESTORS` defaults to
  `'none'` — anything that needs to be framed (e.g. a PDF preview) needs
  this explicitly relaxed.
- **Service-worker staleness** — `serviceworker.js`'s cache-busting relies
  entirely on its own script bytes changing (browsers only re-run
  install/activate when the SW file itself differs). It used to have a
  hardcoded `VERSION = "v2.0.0"` string nobody ever bumped, so already-
  installed clients kept serving first-visit assets forever regardless of
  redeploys. Fixed by interpolating `VERSION` from `settings.VERSION`
  server-side (`myapp.views.service_worker`, registered ahead of
  django-pwa's own route) — every CI version bump now busts the cache
  automatically. A **separate**, more recent fix (already merged, not part
  of PR #189) made the client-side registration explicitly call
  `registration.update()` on every load and reload once on
  `controllerchange`, since Chrome otherwise throttles the byte-diff check
  to once per 24h even after the version string changes server-side.
- **Duplicate-detection, two root causes stacked** — first fix normalized
  `check_duplicate_code` (`myapp/views.py`) with `Lower(Trim(...))` for
  case/whitespace differences. A follow-up report (identical photo, still
  no duplicate warning) turned out to be OCR non-determinism: neither
  `ocr/backends/claude_backend.py` nor `openai_backend.py` set
  `temperature=0`, so default sampling could read a different character at
  an ambiguous glyph on repeat scans of byte-identical images. Fixed with
  `temperature=0` on both, then a photo-hash duplicate-detection layer
  (`myapp/imagehash.py`) was added as a fifth, independent signal. **If a
  "duplicate not caught" bug report resurfaces, check both the text-match
  normalization AND OCR determinism before assuming it's a new bug.**
- **The `dist/js` esbuild bundle is built but not actually wired in** —
  `package.json`'s `build` script runs esbuild on 10 specific JS files
  into `dist/js/*.min.js`, but `myapp/templates/base.html` loads the raw,
  unminified files straight from `myapp/static/assets/js/` — nothing
  references `dist/`. This isn't necessarily broken (unminified JS still
  works fine), but it means running `npm run build` currently has zero
  effect on what's actually served. Flagging so nobody assumes minified
  JS is in production, or spends time debugging why editing `dist/js`
  doesn't change behavior.
- **Historical bug titles worth a targeted `grep -n "^## " FORK_CHANGES.md`
  search if something similar resurfaces** (not deep-dived, just flagged):
  server errors used to be invisible in production (500s swallowed with no
  operator visibility); the item-detail Share button broke because
  Django's i18n URL-prefix redirect silently downgraded a POST to GET;
  "days left" expiry countdowns had an off-by-one from naive date math
  depending on time of day; the PWA's "Viewing cached content" banner had
  two independent false-positive bugs fixed in two separate passes.
